Ring: 2 slots × max_t_(8) × 80 blocks × 36 B = 23,040 B/slot, ~45 KiB per Verifier, ~90 KiB
pinned for a 2-stage split; depth-2 indexed by step parity `k & 1`; seq words = the doorbell's
store discipline (`doorbell_publish_value` pattern: fence, store, fence — no RMW of host memory).

Publish gate (static per verifier, read once at init): `STRATA_HELPER_XQ_RING=1` AND a
window-tier helper configured (`helper_xq_ring_consumer()`, set once by generate.cpp from
`remote_opt != nullptr || helper_tier_p != nullptr`) AND `expert_layout().native` AND `!ar_on()`.
OFF ⇒ no kernel added to the capture, identical graph bytes, identical RSS (allocation is gated).

Service loop: bounded spin on `m_xq_seq_[k&1] >= want` after `set_plan_slot(grp)`, same
discipline as the main doorbell wait (strata_cpu_pause / periodic cudaStreamQuery /
kGpuProgressTimeout / release_gpu_waits on timeout, XQ-NEVER-RANG / XQ-TIMEOUT trace events).
The per-window `m_xq_seq_` reset sits beside the h_seq_/h_flag_ siblings in `stage_inputs` AND
`stage_batch` (both replay record_window graphs, whose captures embed the tail publish).

Consumer: `proxy_begin` takes the ring image when `helper_xq_ring_enabled() && image valid &&
!had_gu(layer) && gu_act != Q8_K && bytes == n_tok*(N/32)*36`; every miss runs today's
`quantize_q8_1_cpu` path verbatim. Q8_K / F32-window arms untouched and still take precedence.
No protocol or wire change.

## Deviations from the plan (evidence in the lane report)

1. **Consumer-presence gate**: the plan's `remote_opt_` never sees the out-of-process
   expert-helper socket tier (`helper_tier_p` is registered only into `drive.d.remote[]`,
   generate.cpp:10358-10366; `set_remote_expert_opt` is called only in the
   --remote-expert-opt deployment, generate.cpp:13081/13163) — gating the publish on it would
   disable F2 in the deployment it targets. Added the one-shot process flag
   `helper_xq_ring_consumer()` (expert_helper_xq_ring.hpp), set by generate.cpp after the tiers
   register.
2. **Exposure mechanism**: the win pool user (`Drive`/`SplitDrive`, generate.cpp) has no path to
   a Verifier, but `ExpertDispatch::plan` already IS the running verifier's `GpuPlanSink`
   (generate.cpp:15841 `drive.d.plan = ver.plan_sink()`). The image flows
   Verifier → `sink_.xq_{image,bytes,valid}` (set after the service-loop wait) →
   `expert_pool_dispatch_multi` (expert_source.cpp:5284) → `RemoteExperts::begin` trailing
   params → `proxy_begin`. `cur_xq()` exists on the Verifier as the plan named it; the
   `PoolMultiFn` signature is unchanged.
3. **stage_batch reset**: the plan anchored only stage_inputs' reset (:3160-3163 then); the tree
   has a second sibling-reset site (stage_batch, verify.cpp:4910-4913) whose slot graphs embed
   the tail publish through the shared record_window — the reset was added there too.
4. **Test case (v)** is exercised host-only at two levels: the protocol discipline through the
   SAME `xq_ring_reset`/`xq_ring_ready` helpers stage_inputs and the service loop call
   (stale-values counterfactual, post-reset gate, window-2 publish), and the tier level
   (window-2 claim frame carries window-2's image). A real graph-replay leg needs the engine
   gates (step c).
5. **QFUSE parity leg** rides `gr_parity --selftest` in the same ctest window (the plan's
   explicitly allowed option; gr_parity.cpp:416 pins the fused read's image to
   native_quantize_q8_1) plus `xq_triple_parity` (rows==native==cpu, direct + graph replay,
   plain + rotated, T 1..8; exits 77 host-only so ctest skips it without a device).
6. **FetchContent**: the golden config clones llama.cpp from github at configure time and this
   host has no github credentials — the build passes
   `FETCHCONTENT_SOURCE_DIR_STRATA_LLAMACPP=<integ f1-tests' populated _deps/src>`; every other
   cache variable is the frozen golden (rpcw-hip.cmake).
