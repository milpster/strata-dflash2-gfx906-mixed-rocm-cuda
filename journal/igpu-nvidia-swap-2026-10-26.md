## Follow-up: zram versus incompressible model data

- Checked official zram and zswap documentation: https://docs.kernel.org/admin-guide/blockdev/zram.html and https://docs.kernel.org/admin-guide/mm/zswap.html.
- Plain zram retains incompressible swap pages at roughly their original RAM cost plus overhead, so a large high-priority zram tier can consume working-set RAM without materially increasing capacity; compression also competes for CPU. Compressible anonymous pages from other processes could still benefit. Actual compression ratio was not measured.
- Clean file-backed model pages normally reclaim by eviction/refault, not swap; genuinely pinned pages are not swap candidates. Adding compression does not directly solve either path.
- A bounded zswap cache over existing swap is a possible later experiment: it can reject incompressible pages and evict cached pages to backing swap. Kernel support/current zswap state was not inspected. Complete the existing one-variable VM-policy comparison before adding compression. No configuration changed.
- Terminology clarification: zram is the kernel compressed-RAM block device; zswap is a compressed cache ahead of backing swap; `zramswap` commonly names a userspace setup script/service (e.g. Debian zram-tools or Arch's zramswap package), not a third kernel memory mechanism. Debian/Arch documentation search corroborated this distinction. No configuration changed.
