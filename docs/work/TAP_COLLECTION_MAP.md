# DFlash cross-GPU tap collection — map (read-only survey, no build, no GPU run)

CONCLUSION: the collection is serial in two separable places — a host-blocking D2H held under the collector mutex on CUDA0's prefill thread, and the drafter's whole 8192-row context fusion run inline on CUDA1's last-stage thread at chunk end with a full stream sync — so the cheap, byte-identical win is to defer that fusion (and the producer copy) off the critical path and let CUDA1 keep computing, not to touch the copies' arithmetic.

Repo HEAD read: branch `build-mixed-v0210`, HEAD `04f13303` ("bench: save consolidated verdict (out/RESULTS.md) + five-arm report"); merge base with upstream `ffa80d73`. No build, no engine, no GPU program was run; production untouched. Static analysis only — every cost magnitude below is UNCONFIRMED unless a measured bench number is cited.

Geometry used throughout (from the live startup anchors + the code that produces them, generate.cpp:7256-7292): 48 layers, split line 32 → stage 0 = layers [0,32) on CUDA0 (the base `sp`), stage 1 = layers [32,48) on CUDA1; drafter and collector live on the LAST stage's device (CUDA1) — generate.cpp:7240,7281. Artifact taps [5,15,25,35,45] with `target_layer_inputs=false` → boundary ids 6,16,26,36,46 (generate.cpp:7184-7190). rows_cap: BF16 = `max(min(prefill_auto_max(8192), max_context), 6144)` = 8192 (generate.cpp:7278-7281, default at 837), FP32 = `kVerifyMaxT` = 8 (verify_kernels.hpp:25, window_limits.hpp:23). So plane = 5*8192*2560*2 + 5*8*2560*4 = 209,715,200 + 409,600 = 200.4 MiB and pinned = 3*2*8192*2560*2 + 3*2*8*2560*4 = 240.5 MiB — exactly the logged "planes 200.4 MiB on CUDA1, pinned staging 240.5 MiB". Foreign taps = 3 (t=0,1,2 → boundaries 6,16,26, produced on CUDA0); local taps = 2 (36,46, CUDA1, pure D2D, never touch the host: dflash_tap_collect.cpp:197,267).

## a. Tap production and consumption

- **Capture site (prefill, our runtime)**: `src/prefill/prefill.cpp:4203-4222`, inside the chunk's layer loop, `half == 0` (the layer body is split `for (int half = 0; half < 2; ++half)` at 4112), right after layer `l`'s hyper-connection projections/mix (4140-4202) and before its attention (GDN at 4228, QSA path alongside). Gate `if (l == m.tap_layers_[ti])` — so the write happens once per boundary per chunk.
  - `target_hc_mean=true` (our artifact): `dflash2_hc_mean(m.R, nullptr, m.taps + ti*m.T*N, T, N, g.hc, m.cs)` (prefill.cpp:4211-4213). Kernel: `src/kernels/cuda/dflash_inco.cu:245-255` — ascending sum over the `hc` streams of `residual[(row*hc+h)*hidden+c]`, divide by `hc`, `bf16_from_f32`. This is the log's "(HC stream mean capture)" (generate.cpp:7290). It runs on the stage's **prefill stream `m.cs`**, on the compute critical path, not on any staging path.
  - `target_hc_mean=false` shape (not our artifact): `f32_to_bf16_bulk(m.mixed, …)` (prefill.cpp:4215-4217) — the contracted attn-half residual.
- **Plane layout**: one BF16 plane per stage, allocated inside the prefill carve: `m.taps = o.take<uint16_t>(n_taps_ * T * N)` (prefill.cpp:1996), stride = the chunk capacity `tap_stride_rows() = impl_->T` (prefill.cpp:2518), tap `t`'s rows at `taps + t*stride*N` (prefill.hpp:246-250). Single-buffered per stage: chunk N+1 overwrites rows [0,T) of the same slices.
- **Why boundaries {6,16,26,36,46}**: the artifact's `target_layers` are layer *outputs* 5,15,25,35,45; the capture is taken at the *input* of the next layer (plan header, `include/strata/core/dflash_tap_plan.hpp:2-4`: "completed layer outputs [5,15,25,35,45] captured at the NEXT-layer boundary, i.e. boundary id tap+1"). Structurally "boundary N<-CUDAk" = tap `N-1`'s rows are written by the stage whose layer range contains layer `N` (ownership by range containment: dflash_tap_plan.hpp:69-86, `owner[t]`), and that stage runs on CUDAk (`dev[owner[t]]`, dflash_tap_plan.hpp:101). Stage ranges/devices come from `split_at` at startup (generate.cpp:7256-7267); stage 0 = base `sp` is index 0, later stages are `i+1` (generate.cpp:10785,11281,11285-11287).
- **Producer callback sites (prefill)**: `Prefill::dflash_on_taps` (prefill.hpp:251-255) fires (1) in the hand-off path for every stage **with a successor**, after the hand-off drained this chunk's stream and *before* the successor's chunk for the same key is submitted: prefill.cpp:6548-6560 (the L14 root-cause fix); and (2) at the chain's LAST stage after a full `cudaStreamSynchronize(m.cs)`: prefill.cpp:6624-6636 (sync 6626, then `on_stage_chunk`, `on_chunk`, `dflash_on_taps`). Wiring: base at generate.cpp:10776-10788 (stages `Slice{0,…}`), per stage at generate.cpp:11270-11335; the last stage's callback additionally runs `assemble()` and feeds the drafter.
- **Consumer = first real use of a chunk's rows**: inside the last stage's callback, immediately after `assemble()` — `dflash.add_context(tc.plane_bf16(), n_taps, stride_rows_bf16, pos, rows, e)` (generate.cpp:11299-11300). `add_context` (`src/core/dflash_runtime.cpp:759-820`) gathers each 8-row batch from the plane (`dflash_gather_taps`, 786) and runs the fusion (fc → rmsnorm → bf16 → q8 prepare → per 5 draft layers k_proj/v_proj/k_norm/rope/KV-append, `fusion_rows` 900-1010) on the drafter's stream `cs_`, in `rows/8` host-loop iterations (782), ending in a full `cudaStreamSynchronize(cs_)` (798).
  - Per chunk that is `8192/8 = 1024` batch iterations ≈ 30 kernel launches each (gather, fc, rmsnorm, to_bf16, quantize prepare, 5×{k_proj, v_proj, k_norm, rope, append}) ≈ ~30k launches/chunk. Static FLOP estimate: fc `2*12800*2560` + 5 draft layers `2*2*2560*1024` ≈ 91 MFLOP/row → ≈ 750 GFLOP per 8192-row chunk. **These magnitudes are estimates from the code shape, not measurements.** Cheap confirmation exists and was NOT run here: `STRATA_DF_EVENTS=1` per-section GPU timing on the drafter stream (dflash_runtime.cpp:99,175,354; sections named `fusion.fc_gemv`, `fusion.k_proj`, …).
- **Slack that exists today** (the ordering facts that bound any deferral):
  - Producer→consumer slack: stage 0 stages chunk N at stage 0's chunk N end (prefill.cpp:6560); the consumer needs chunk N's rows at CUDA1's chunk N end, which is ≈ one chunk of CUDA1 compute later. The collector's 2 slots (`kSlots`, dflash_tap_collect.hpp:88) encode exactly that one-chunk pipeline depth.
  - Fusion slack: with `--dflash` on a layer split, `--pipeline-windows` is refused (generate.cpp:5674-5676) so `pipe == false` (generate.cpp:11601) — no verify window and no `propose()` runs during the prompt read. The drafter's appended context cells are first READ by the first `propose()` after prefill (generate.cpp:19774, 21767). So chunk N's fusion may legally finish anywhere before prefill ends; today it is forced to finish before CUDA1 launches chunk N+1.

## b. The staging loop, streams, events, memcpys, and every sync

Call graph per prompt chunk, in order:

1. CUDA0 (base `sp`, host thread = the CUDA0 prefill thread), chunk N end:
   - hand-off drains the chunk: `cudaEventSynchronize(m.hand_done[buf])` (prefill.cpp:6536) or `cudaStreamSynchronize(m.cs)` (6541) — rows complete.
   - `on_stage_chunk` then `dflash_on_taps` (6547,6560) → `DFlashTapCollector::stage(key=pos0, Slice{stage, sp.taps_plane(), stride, rows}, 2, err)` (generate.cpp:11278-11283).
   - Inside `stage()` (`src/core/dflash_tap_collect.cpp:178-226`): `mu_` LOCKED at 180 and held until return; `acquire_slot` (200) with backpressure `cv_.wait` (61, mutex released); `s.rows` geometry guard (203); **`cudaEventSynchronize(s.ev)`** (205) — drains this slot's previous H2D; then, per owned foreign tap: `OnDevice on_producer(plan_.dev[slice.stage])` (213) and a **blocking `cudaMemcpy(pin[t], plane + t*stride*N*type, rows*N*type, cudaMemcpyDeviceToHost)`** (214-219). Bytes: 8192*2560*2 = 40.0 MiB per foreign tap, 3 taps = 120 MiB per chunk, all serialized on one host thread, inside the mutex. `cv_.notify_all()` at 222.
2. CUDA1 (last stage, host thread), chunk N end: full `cudaStreamSynchronize(m.cs)` (prefill.cpp:6626) → `on_stage_chunk`, `on_chunk`, `dflash_on_taps` → `stage()` for its own slices (no-op: its taps are drafter-local, dflash_tap_collect.cpp:197) → `assemble()` (generate.cpp:11288) → `add_context` (11300).
   - Inside `assemble()` (dflash_tap_collect.cpp:228-353): `mu_` LOCKED at 231; device assertion (236-238); validate-every-tap guard (243-268); `acquire_slot` (269); the L14 consumer ordering (283-324: fast refusal if no flags; else bind `awaiting` and `cv_.wait_until` bounded by `kAssembleWaitMs = 10000` — dflash_tap_collect.hpp:94); then, per tap, on the drafter stream `cs_` only: `cudaMemcpyAsync(dst, src, rows*N*type, cudaMemcpyDeviceToDevice, cs_)` for drafter-local taps (335) and `cudaMemcpyAsync(dst, s.pin[t], rows*N*type, cudaMemcpyHostToDevice, cs_)` for foreign taps (339) — 2×40 MiB D2D + 3×40 MiB H2D per chunk; slot retire + `cudaEventRecord(s.ev, cs_)` (344-350); `cv_.notify_all()` (351).
   - `add_context` then launches the fusion on the same `cs_` (dflash_runtime.cpp:782-801) and blocks the host in `cudaStreamSynchronize(cs_)` (798).
3. Streams involved (created, not shared):
   - per stage: `m.cs` (main prefill compute, given by the caller's `st.stream`, generate.cpp:11351), `m.copy` (expert-streaming H2D ring: prefill.cpp:1819, used 3799-3969), `m.ple_copy` (1920), `m.kv_copy` (3338), `m.hp_cs` (5148), peer/prompt-helper streams `pp->s/s_out/s_cp/x_stream` (2430-2432,2586).
   - drafter: `cs_` = `cudaStreamCreateWithFlags(cs_, cudaStreamNonBlocking)` (dflash_runtime.cpp:349) — **default priority, single stream**; the collector writes the assembled plane only on `cs_` (`set_stream(dflash.stream())`, generate.cpp:7285; dflash_tap_collect.hpp:158,200).

**What makes it serial** — separated into real ordering needs vs accidental serialization:

Real data/consumer requirements (must survive any change):
- The producer's plane rows must be complete before its D2H — already guaranteed by the drain at prefill.cpp:6536/6541/6626.
- A pinned slot must not be rewritten while its H2D is still reading it — `s.ev` drained at dflash_tap_collect.cpp:205, recorded at 347.
- Plane readers/writers must be ordered — today ALL plane writes go on `cs_` (335,339), so stream order is the whole mechanism (dflash_tap_collect.hpp:14-17).
- The consumer's `assemble(key)` must see its key's producers staged — the L14 contract, enforced by flags + the bounded epoch-guarded wait (hpp:41-51, cpp:283-324).
- Unconsumed staging is never evicted; slot lifecycle EMPTY/STAGED/RETIRED (hpp:105-109, cpp:36-45).
- Drafter ring appends must be gapless and position-monotonic (dflash_runtime.cpp:773-781,802).

Accidental serialization (the exploitable part):
- **`mu_` is held across the D2H copy** (cpp:180 lock, 214 copy, released at function end) — so CUDA0 staging a chunk and CUDA1 assembling a chunk cannot overlap at all, in either direction (cpp:231).
- **The D2H is a blocking `cudaMemcpy`** (cpp:214) on the producer's host thread — CUDA0's prefill thread stalls ~120 MiB worth of PCIe, and because the producer fires *before* the successor's chunk is submitted (prefill.cpp:6560 vs 6568-6579) it also delays CUDA1's chunk N+1 launch.
- **The consumer runs the entire fusion synchronously on the last stage's thread** with a full stream sync (dflash_runtime.cpp:782-801), so CUDA1's card idles (no chunk N+1 in flight) for the whole staging+fusion tail, and the next chunk's launch is host-gated. Nothing consumes those rows until after prefill (section a).
- **Pipeline depth is 2 slots** (hpp:88) and the plane is single-buffered per stage (prefill.cpp:1996) — the only existing overlap is "stage N+1's pinned copy while N is unconsumed", and it is neutralized by `mu_`.
- **One drafter stream at default priority** (dflash_runtime.cpp:349): nothing lets staging copies sit beside compute with a priority guarantee.

## c. Concurrent work during a prompt chunk, and where staging blocks it

- CUDA0 (layers 0-31): `m.cs` runs the layer bodies (HC GEMMs, GDN/QSA attention, MoE, quantize/act), `m.copy` streams non-resident experts H2D (prefill.cpp:3799-3969, waits wired via `cudaStreamWaitEvent(m.cs, m.copied[slot])` at 3990-4005), hand-off piece D2H on `m.cs` (6527-6535). Tap staging inserts (i) the 5 boundary `hc_mean` kernels on `m.cs` inside the layer loop (4211-4213), and (ii) a 120 MiB blocking host D2H **between chunk N's completion and chunk N+1's launch** (6560), ahead of the successor submit (6568-6579).
- CUDA1 (layers 32-47): its own `m.cs` + `m.copy` + hand-off upload waits (prefill.cpp:3498-3516). The drafter's `cs_` carries the collector's H2D/D2D (cpp:335,339) and the whole context fusion (dflash_runtime.cpp:782-801). Today all of that runs while CUDA1's `m.cs` is drained and has nothing queued (prefill.cpp:6624-6636 is the chunk tail) → the fusion owns the card, and CUDA1's utilization dips by the tail length per chunk; CUDA0 keeps computing (the chain is one chunk apart, prefill.cpp:6638-6639 "an intermediate stage can return while later GPUs are still processing the previous chunk").
- Decode/verify side (for reference; must stay intact): each stage's verifier carves and captures its own FP32 taps (verify.cpp:1006,1075; capture at 2510-2521 via `df2_tap_gr`/`hc_mean_streams`, and `dflash2_hc_mean` at 1639-1640) on its verifier stream; the consumer is `df_collect_f32` (generate.cpp:12104-12127, same `stage()`+`assemble()` with `type_bytes=4`, rows ≤ 8) then `add_context_f32` (17278, 19738-19742 with `sync_context`), then `propose` (19774). Per-window foreign bytes are only 3*8*2560*4 ≈ 246 KiB, so the decode cost is host-sync latency, not bandwidth.
- The RTX 3080 prompt tier (arm D, `STRATA_PREFILL_HELPER=0`) is a *separate* per-layer claim/send/reply round-trip on the stage's thread (prefill.cpp:4938-5189, 6281-6290) — it is not part of the tap path; bench/ab-v0210/out/RESULTS.md:29 attributes it ~1/3 of the 80k gap.

## d. Knobs, sizers, and the upstream-overlap question

Tap path / capacity:
- `bytes_needed_impl` loan pricing: the tap plane is taken in the carve at prefill.cpp:1996 and priced in the loan only by the restored `if (g_n_taps > 0) o.take<uint16_t>(g_n_taps * T * g.n_embd)` at prefill.cpp:2886 (commit 4436fcfc, `src/prefill/prefill.cpp` +1 line; the same commit enriched the guard text in dflash_tap_collect.cpp:249-260). `g_n_taps` mirrors `set_tap_layers` (prefill.cpp:2521-2526). Consequence: with `--dflash` on a split, every stage's prompt loan is bigger by `n_taps*T*N*2` (40 MiB at T=8192) and CUDA1's drafter card additionally holds the 200.4 MiB plane + the drafter pools (generate.cpp:7304-7305 logs 580.6 MiB held).
- `--dflash-block` / `--spec`: sets the effective draft length `dflash_k = min(dflash_block, spec-1, trained)` (generate.cpp:7196-7215). It changes the decode window width and the drafter's propose work — it does NOT change tap staging bytes (per-chunk rows = the prefill chunk; per-window rows = T).
- `--prefill` chunk / `--prefill-auto` ceiling: sets `reach_rows` → `bf16_rows` → plane + pinned size (generate.cpp:7278-7281) and the number of per-chunk tails. Guarded refusals if a chunk exceeds the cap: "producer rows exceed the plane capacity/stride" (cpp:189), "assemble rows exceed the plane capacity" (cpp:235). Fewer, larger chunks = fewer tails; plane/pinned scale linearly (16384 → 400 MiB plane, 480 MiB pinned).
- **`--layer-split` line position = free control of how many taps are foreign** (dflash_tap_plan.hpp:69-98): a split at 16 leaves only boundary 6 foreign (40 MiB/chunk D2H+H2D instead of 120) at the cost of load imbalance (CUDA1 then runs 32 of 48 layers). No code change. UNCONFIRMED net PP effect — needs a measured arm.
- `STRATA_HANDOFF_PIPE[=P]` (prefill.cpp:449-476, 6520-6580, 3498-3516): pipelines the split's *row hand-off* in P pieces on events. Overlaps stage-to-stage row transfer; touches no tap buffer. `STRATA_HANDOFF_PIPE_WORKER=0/1` picks thread-per-chunk vs one worker thread.
- `--pipeline-windows` / `STRATA_PIPELINE_AUTO`: the engine's real overlap mode (two verifiers per parity so stage 0 runs window K+1 while stage 1 reads window K) — **explicitly refused for `--dflash` on a layer split** ("the cross-GPU tap collector is serial", generate.cpp:5674-5676); the collector's own header says the same (dflash_tap_collect.hpp:62).
- `STRATA_DF2_PRIO` (dflash2.cpp:213-224): high-priority drafter streams `cs_`/`cs2_` — upstream's drafter only; not in our runtime (dflash_runtime.cpp:349 has no priority) and compiled out in prod.
- `STRATA_DF_EVENTS=1` (dflash_runtime.cpp:99,175,354) and `STRATA_DF_DBG` (763,790-793,950-958,991-993): per-section timing/probes; the DBG path ADDS stream syncs (diagnostic only — do not enable in prod).
- `STRATA_DF_PDL` (include/strata/kernels/pdl.hpp:16-33): programmatic dependent launch edges in the drafter, always false on HIP. Affects decode-round kernel latency, not staging.
- `STRATA_DFLASH_TAPS=<file>` (generate.cpp:1995, 20627, 21621): tap fixture dump (target-only capture); no staging effect.
- `STRATA_DFLASH2_SERIAL_SELECT`/`_TOPK`/`STRATA_DF2_*`: upstream runtime's decode-side knobs (dflash_inco.cu:235-242 etc.); no staging effect.
- `STRATA_HC_SPLIT` (kernels/cuda/fused_gr.cu:1742-1744, include/strata/kernels/fused_gr.hpp:91-93): selects the hyper-connection **read kernel variant** (0 plain / 1 split / 2 staged). Unrelated to tap staging; it is the "HC" in `gr_*`, not the "HC stream mean". No effect on the collector.
- `STRATA_HC_Q8`, `STRATA_HC_UPMIX`, `STRATA_HC_REQ8`, `STRATA_HC_PERSIST`, `STRATA_HCD_EXACT`: HC GEMM/read variants on the prefill compute path (prefill.cpp:4140-4202) — they change the compute beside which the boundary `hc_mean` kernel sits, so they shift the *relative* weight of the capture kernel, not the staging.

## e. Failure paths and the invariants a reordered staging must keep

- The guard: "producer rows do not cover the assembled rows - refusing a stale read (tap … owner … slice stage … plane NULL|ok rows R > stride_rows S or slice rows r)" — dflash_tap_collect.cpp:243-268, text expanded by 4436fcfc. It fires per tap when the plan's owner has zero/multiple slices, a null plane, `rows > stride_rows`, or `rows > slice.rows`; plus "tap t has N producer slices" (262-266).
- "tap t was never staged" (288, 318) / fast refusal when a key has zero staged flags (286-289); bounded 10 s consumer wait with the `awaiting` binding (290-324, hpp:101,108-109); "staging cancelled (request reset/disabled mid-wait)" on epoch change (65-68, 312); backpressure "both slots hold unconsumed staging" (43-45).
- Ring reset semantics: `ring_state_.reset()` only at `pos0 == 0` (dflash_runtime.cpp:778 for the prompt path, 836 for the verify path); appends must be gapless/monotonic (`append_allowed` 779-781, `note_append` 802/845). Collector-side reset: `reset_staging()` once per request at serve request start (generate.cpp:16127), which bumps `gen_` and wakes every waiter (cpp:162-176).
- Invariants to preserve so the guards stay silent under reordering:
  1. Every tap keeps exactly ONE producer slice per `assemble()` call, with `plane != nullptr` and `slice.rows >= rows` — do not "optimize away" a slice's `assemble` appearance (that is what L15 fixed: the null slice must be legal for staging only when it owns no foreign tap, cpp:184-198, generate.cpp:12119-12125).
  2. Producer-before-consumer per key stays: `staged[]` flags are the contract; if a copy becomes async, "staged" must mean "safe for the consumer to read on `cs_`", i.e. pair it with an event the consumer's H2D waits on — never let the flag mean "bytes will arrive eventually".
  3. The plane's per-chunk reuse stays single-stream: all writes on `cs_`; a producer-side plane writer added on another stream needs an explicit event.
  4. Slot lifecycle stays: unconsumed STAGED never evicted; RETIRED slots drained via `s.ev` before host rewrite (cpp:205).
  5. Append order on `cs_` stays position-ascending (single drafter stream, host-enqueued in chunk order).
  6. Cancellation stays epoch-guarded: a reset/disable mid-wait rejects the old request's producer (cpp:53-70).

## Ranked candidate interventions (all pure scheduling unless stated)

1. **Defer the consumer's context fusion off the last stage's critical path** (lowest risk, biggest expected share).
   Change shape: `add_context` gains a "defer" mode — keep the same per-8-row gather+`fusion_rows` launches on `cs_` (dflash_runtime.cpp:782-794) and drop/defer the full `cudaStreamSynchronize(cs_)` at 798; the last stage's callback (generate.cpp:11299-11300) enqueues and returns; add one flush (`cudaStreamSynchronize(cs_)`, existing `idle()` — dflash.hpp:223-226) at prompt-read end, before the first `propose()` (generate.cpp:19774/21767) and before any drafter checkpoint/snapshot.
   Why byte-identical: identical kernels, identical order, identical stream (`cs_`), identical bytes; only the host stops waiting mid-prompt. Plane reuse is protected by `cs_` stream order (all plane writes are at cpp:335/339) and the slot's `s.ev` already records the H2D (cpp:347); the ring's monotonic appends are host-issued in chunk order on one stream.
   Expected effect: removes CUDA1's per-chunk idle tail (fusion + 30k launches + sync) from the prefill critical path — the bench attributes ~2/3 of the 80k gap and ~100% of the fresh gap to the dflash prompt path (bench/ab-v0210/out/RESULTS.md:28-29); the recoverable share is UNCONFIRMED and must be measured with `STRATA_DF_EVENTS=1` first.
   Main risks: (a) fusion now competes with CUDA1's chunk compute for SMs/copy engines, so the gain is partial and chunk throughput may shift (bitwise output unchanged, timing moves); (b) an append failure surfaces after prefill — the request must still fail identically (`add_context` errors are fatal today, generate.cpp:11299-11300 returns false → the prefill run fails); deferred launches make the error arrive on the flush, which must map to the same failure path; (c) any code that reads drafter pools mid-prompt (parity dumps, checkpoints, `--dflash-remote-only` probes) must be checked for ordering.
2. **Producer-side async D2H on the stage's own stream + event, with the mutex released before the copy.**
   Change shape: `stage()` (dflash_tap_collect.cpp:178-226) keeps acquire + geometry + `s.ev` drain under `mu_`, releases the lock, then enqueues `cudaMemcpyAsync(pin[t], plane_slice, bytes, DeviceToHost, m.cs)` (the producer's stream, passed in via `Slice`) and records a per-slot completion event; `assemble()`'s foreign H2D adds `cudaStreamWaitEvent(cs_, slot_d2h_event)` before `cudaMemcpyAsync(..., HostToDevice, cs_)` (cpp:339). Wiring in generate.cpp:11278-11283 passes the producer stream.
   Why byte-identical: same source bytes, same pinned destination, and the copy is stream-ordered ahead of chunk N+1's boundary writes on the same stream (`m.cs`), so no double-buffer of the plane is needed. The copy moves onto CUDA0's copy engine beside CUDA0's chunk N+1 compute.
   Expected effect: removes ~120 MiB/chunk of host-blocking stall plus the mutex serialization with `assemble()`; recovers part of the fresh gap and part of the 80k gap.
   Main risks: cross-device event consumption (CUDA0 event waited on CUDA1's `cs_`) must be confirmed on ROCm gfx906 with `HIP_FORCE_P2P` — UNCONFIRMED, verify with the existing 2-GPU fixture `dflash_tap_collect_test`; slot semantics change from "staged = complete" to "staged = enqueued", so the L14 guard's meaning must be re-verified (the flag gate stays, the read is event-ordered); a reset/disable racing an enqueued D2H needs the epoch check to cover the pinned rows.
3. **Split-line knob experiment (no code at all)**: run the bench arms with the split line at 16 (only boundary 6 foreign) and at 40, and with `--prefill 16384`. Zero risk to numerics (ownership and plane sizing are computed from the split at generate.cpp:7256-7281); tells us how much of the gap is bytes vs tails vs the drafter-card VRAM carve. Main risk: load imbalance / plane growth (400 MiB plane + 480 MiB pinned at 16384) eating CUDA1's expert cache — i.e. paying in a different currency.
4. **Parallel H2D copies for the foreign taps on a second CUDA1 stream + event join.**
   Shape: an extra staging stream in the collector, one `cudaMemcpyAsync` per tap, event join before `add_context`'s first gather. Byte-identical (same bytes, plane writes still ordered by the join before the readers).
   Expected effect: small — the 3 copies already run back-to-back on one stream and are limited by the single PCIe link, not by stream count; the copy-engine count per card on gfx906 is UNCONFIRMED (check with a device query before writing code).
   Main risk: plane-write ordering must be re-established by the join event (today `cs_` stream order does it) — a missed join is exactly the "refusing a stale read" guard firing, i.e. loud, not silent.
5. **Fuse the HC stream mean into the boundary's existing HC read (kill the standalone `hc_mean` kernel).**
   Shape: extend `gr_mix_r`/`gr_write_norm_rs` (prefill.cpp:4112-4222, `src/kernels/cuda/fused_gr.cu`) with a plane write at the boundary layers, reproducing `hc_mean_kernel`'s exact ascending sum, `/hc`, `bf16_from_f32` (dflash_inco.cu:245-255).
   Why NOT purely scheduling: it changes the arithmetic site, so bit-identity must be proven (parity fixtures: `src/core/dflash2_parity.cpp`, `tools/dflash_ref.py --taps`).
   Expected effect: removes 5 kernels/chunk that each read `T*hc*N` fp32 (static estimate ~335 MB read, ~42 MB write per boundary → low single-digit ms/chunk). Smallest expected gain of the list.
   Main risk: divergence from the reference taps → drafting acceptance shifts, which the brief forbids degrading.
6. **Do not start with: removing the `--pipeline-windows` + dflash + split gate** (generate.cpp:5674-5676). It is the deepest overlap mode, but it puts concurrent verify windows on the tap keys, needs slot depth > 2, and interacts with the drafter ring horizon (dflash_runtime.cpp:773-781) — highest risk, and the collector's own header calls the design serial-only (dflash_tap_collect.hpp:62).

Decode-preservation note for every intervention above: the decode path uses `df_collect_f32` → `add_context_f32(..., sync_context)` → `propose` (generate.cpp:19674-19775). Only intervention 1 touches a function the decode path shares (`add_context`'s sync), and only through a parameter whose default keeps today's `synchronize=true` semantics; the verify-side call already passes an explicit `sync_context` flag (19742), so it is unaffected. The +40% decode win comes from the drafted window (19774), untouched by 1-5.
