# DFlash cross-GPU tap collection — overlap design gate (2026-11-03)

DECISION: ship intervention 1 (defer the consumer's context fusion, with a same-device D2D-completion gate) as the F1 prototype and intervention 2 (producer-side async D2H on a staging worker thread, no cross-device stream event) as an independent second opt-in flag, both default off, one compile, so the window bisects them as F1 / F1+F2.

Written by the design gate from the branch `build-mixed-v0210` (HEAD `116c5217`; map read at `04f13303`). No build, no GPU program, no engine run, production untouched. Every design claim cites file:line; anything not measured here is marked UNCONFIRMED. Basis: `docs/work/TAP_COLLECTION_MAP.md` (parent-verified), plus the anchor re-reads listed in §8.

## 0. Why this scope

- The tail is the drafter's fusion drain: `add_context` runs 8192/8 = 1024 host-loop iterations per chunk, gather + `fusion_rows` (fc_gemv / rmsnorm / to_bf16 / 5×{k_proj, v_proj, k_norm, rope, kv_append}) ≈ 30k launches, ending in a full `cudaStreamSynchronize(cs_)` (`dflash_runtime.cpp:782-794`, `925-1002`, `798`), fired from the last stage's chunk tail (`prefill.cpp:6624-6633`, callback at `generate.cpp:11299-11300`). Nothing reads the fused cells before the first `propose()` after prefill (`generate.cpp:19774`, `21767`) because `--pipeline-windows` is refused for `--dflash` on a split (`generate.cpp:5674-5676`, `pipe == false` at `11601`).
- The producer's stall is 120 MiB/chunk of blocking D2H **inside** the collector mutex (`dflash_tap_collect.cpp:180` lock, `214-219` copy), and it fires *before* the successor's chunk is submitted (`prefill.cpp:6560` vs `6568-6579`), so it host-gates CUDA1's chunk N+1 launch.
- Measured share (cited as given, `bench/ab-v0210/out/RESULTS.md:22-29`): fresh 18233 PP 305.7 (B) vs 337.2 (C stock) vs 337.6 (E no-dflash) — the whole gap is this path; 80k 444.9 / 550.4 / 541.6 — ~2/3 of that gap is this path. Per 8192-row chunk the tail is ~1.8-2.3 s. Decode +48% (33.1 vs 23.6) must not degrade.
- Bytes alone cannot explain the tail: 120 MiB D2H per chunk ≈ tens of ms, not ~2 s. The launch-bound fusion drain is the dominant term. This is the hypothesis the window's first probe (step a) tests before any code.

Interventions 5 (arithmetic) and 6 (pipeline-windows gate) stay out (§6).

## 1. Flags (naming follows the `STRATA_DF_*` family: `STRATA_DF_EVENTS` `dflash_runtime.cpp:354`, `STRATA_DF_DBG` `763`, `STRATA_DF_PDL` `pdl.hpp:16-33`)

- `STRATA_DF_DEFER_CTX=1` — intervention 1 (F1).
- `STRATA_DF_ASYNC_D2H=1` — intervention 2 (F2). Independent of F1, default off.
- Both read once into a static bool at drafter upload (`dflash_runtime.cpp:332-357`) / collector enable (`dflash_tap_collect.cpp:85-134`), never per chunk, and printed in the existing startup line (`generate.cpp:7286-7292`, which already logs "cross-GPU tap collection serial on CUDA1: … planes 200.4 MiB … pinned 240.5 MiB"). The window runner must see `defer=1 async_d2h=0` in that line to know which mode the binary booted — no silent mode.
- Flag off ⇒ today's code path, byte-for-byte. The new code is only reachable behind the flag.

## 2. Exact change list

### F1 — defer the consumer fusion (intervention 1)

1. `dflash.hpp:179-180` / `dflash_runtime.cpp:759-760`: `add_context(..., std::string& err, bool sync_context = true)` — the same convention `add_context_f32` already uses (`dflash.hpp:184-185`). Default `true` ⇒ every existing caller is unchanged, including the decode path, which already passes its flag explicitly (`generate.cpp:19742`, `sync_context` defined at `19667`). `add_context_f32` is NOT touched.
2. `dflash_runtime.cpp:798-801`: gate the full `cudaStreamSynchronize(cs_)` on `sync_context`. Keep verbatim, in this order: `upload`/geometry guards (`761`, `769-772`), ring reset and `append_allowed` (`778-781`), the 8-row enqueue loop (`782-794`), `note_append` (`802`). All host-side checks stay synchronous — they are host logic before any launch, and the ring's gapless/monotonic contract (`dflash_ring.hpp`, `dflash_runtime.cpp:773-781`) is host state keyed by enqueue order on one stream.
3. The parity branch (`803-818`) stays inside `add_context` and is enqueued on `cs_`; `parity_dump_u16_as_f32` does its own `cudaMemcpyAsync` + `cudaStreamSynchronize(cs_)` (`57-60`), so under deferral the STRATA_DF_PARITY path re-drains `cs_` at cycle 0. Diagnostic-only, byte-identical, no change.
4. Move the plane-read barrier into `assemble()`: `dflash_tap_collect.cpp:328-343` — after the drafter-local D2D enqueues (`335`) and before the foreign H2D enqueues (`339`), record an event on `cs_` and, in defer mode, `cudaEventSynchronize` it on the consumer (last-stage) host thread. Same device, same device's stream — the exact pattern the producer already relies on at `205` (drain the slot's `ev`, recorded on `cs_` at `347`). The barrier covers only the 2×40 MiB D2D, not the fusion.
   - Required by §3 hazard H1. Without it the deferral is formally racy.
5. Call sites: `generate.cpp:11300` (split chain's last stage) and `generate.cpp:10784` (single-GPU, collector disabled) pass `!df_defer_ctx`.
6. Flush: `propose()` entry (`dflash_runtime.cpp:1041-1050`) gains `if (deferred_) { sync cs_; deferred_ = false; }` before any enqueue, reporting the existing text `dflash: prompt context consumption failed` (`799`). One choke point covers both lanes (serve `19774`, CLI `21767`) and keeps the failure path identical: `add_context` false → callback false → prefill fails (`prefill.cpp:6633`); a deferred execution fault lands on the same string.
   - `propose()` already ends with `cudaGraphLaunch(…, cs_)` + `cudaStreamSynchronize(cs_)` (`1485`, `1493`), so the first propose is *already* ordered after the deferred fusion by stream order. The entry flush buys earlier, better-attributed errors, not correctness.
7. Non-propose exits must flush with the existing `idle()` (`dflash.hpp:223-226`): prompt-only requests (`max_new == 0`), and `conversation_kv_save` of the drafter pools in the park path (`generate.cpp:12540-12552` — the pool read at `12544` runs *before* the stage `cudaDeviceSynchronize()` at `12556`, so it needs its own barrier). Request teardown is already safe: `release()` syncs `cs_` (`dflash_runtime.cpp:267`).

### F2 — producer-side async D2H (intervention 2), worker-thread form

8. `dflash_tap_collect.cpp:178-226`: keep under `mu_` — `enabled()`/rows-cap/geometry guards (`181-192`), `acquire_slot` (`199-201`), rows agreement (`203`), and the pinned-reuse drain (`205`). Release the lock; then per owned foreign tap enqueue `cudaMemcpyAsync(pin[t], plane + t*stride*N*type, bytes, DeviceToHost, producer_stream)` on the **producer's own stream** (`m.cs`, CUDA0) and record a per-slot per-tap event on that stream. Hand (slot, key, tap, event, epoch, pinned ptr) to a single staging worker thread.
9. `Slice` (`dflash_tap_collect.hpp:78-86`) gains a `cudaStream_t stream = nullptr` field; `generate.cpp:11281` and `11285-11287` pass `st.stream` / `sp`'s stream (the streams exist per stage, `generate.cpp:11351`, `11365`; prefill's own `m.cs` is that stream). Decode callers (`12104-12127`) pass `nullptr` ⇒ F2 inert on the decode path.
10. The worker (one thread, created at `enable()`, joined at `disable()`) does `cudaSetDevice(producer_dev)` + `cudaEventSynchronize(ev)` (same device) and then, under `mu_`, sets `s.staged[t] = true` if `gen_ == epoch`, else drops the flag and `cv_.notify_all()` (the epoch contract `53-70`, `162-176`). A copy fault is recorded as a sticky per-kind error + message under `mu_`; `assemble()`'s bounded wait (`283-324`) checks it and returns that message, so the failure arrives on the consumer's side of the same fatal path (`prefill.cpp:6633` → request fails) with the current text `dflash: tap collect: D2H of the producer slice failed` (`217`).
11. **No cross-device event is needed and none is added.** "staged" keeps its exact L14 meaning — bytes complete and drained — because the flag is set only after a same-device host drain. The consumer's existing bounded, epoch-guarded wait (`hpp:94` `kAssembleWaitMs = 10000`, `cpp:290-324`) is the synchronization; it already exists, is already the L14 root-cause fix (`prefill.cpp:6548-6560`), and already tolerates late flags. Invariant 2 of the map's §e is therefore preserved *unmodified*; the "staged = enqueued" semantic change is NOT taken.
    - Evidence the cross-device *host* event sync already works on this stack: `205` drains an event recorded on CUDA1's `cs_` from CUDA0's producer thread, in production, all bench rounds clean (`RESULTS.md:16`). The unconfirmed piece was cross-device *stream* consumption (`cudaStreamWaitEvent(cs_, ev_from_CUDA0)`), which this design deliberately avoids.
12. `reset_staging()` (`162-176`) and `disable()` (`136-159`) must also drain the new per-slot D2H events (pinned rows are written by CUDA0, read by CUDA1). `reset_staging` runs at request start (`generate.cpp:16127`) on the drafter device (`164`), so the drain is a cross-device host sync — the proven pattern (see 11). `disable()` frees pinned rows: it must drain D2H events on the producer device first (set device, sync), same as it already drains every recorded H2D (`125-128`).

### Deliberately NOT in the prototype

- No stream priority on `cs_` today (`dflash_runtime.cpp:349` creates it `cudaStreamNonBlocking`, default priority; upstream's `STRATA_DF2_PRIO` at `dflash2.cpp:213-224` is upstream's drafter only, compiled out in prod). Adding priority is a **follow-up knob (arm P)**, not part of this prototype: it changes scheduling non-deterministically (timing, not bits), confounds the F1/F2 bisect, its gfx906 support under `HIP_FORCE_P2P` is UNCONFIRMED, and its most likely effect is starving the prefill stream the measurement is about. Decide arm P only if F1 shows the fusion tail is SM-contended (per §4).

## 3. Ordering and lifetime analysis

Producer stage planes are read in exactly two places: the producer's D2H (`dflash_tap_collect.cpp:214`, producer device) and the drafter-local D2D at `assemble()` (`335`, src = the producer's stage plane, on `cs_`). Boundary writes into a stage plane happen on that stage's compute stream (`prefill.cpp:4211-4213` → `dflash_inco.cu:245-255`), and each stage plane is single-buffered per chunk (`prefill.cpp:1996`, stride = `impl_->T`, `2518`).

- **H1 (real, must be fixed — the map's §1 "plane reuse is protected by cs_ stream order" is NOT true for producer stage planes).** CUDA1's own stage plane is read by the D2D on `cs_` for taps 36/46 (owner = last stage, `dflash_tap_plan.hpp:69-86` range containment; slice list built at `generate.cpp:11285-11287`) while CUDA1's chunk N+1 writes the same rows on `m.cs` at its 4th layer. Today the host sync at `798` is the only ordering. F1 removes it, so F1 must add the same-device barrier of change 4. Practically the window is small (D2Ds are at the head of `cs_`'s queue, the first N+1 write is ~4 layers in), but a design must not rest on that.
- **CUDA0's producer plane under F2 is safe by stream order**: the D2H is enqueued on CUDA0's `m.cs` at `prefill.cpp:6560`, ahead of chunk N+1's submits at `6568-6579`, same stream.
- **Assembled plane** (`plane_bf16_`, single-buffered per kind, `dflash_tap_collect.cpp:329`): every writer is on `cs_` (`335`, `339`), every reader is `add_context`'s gathers (`dflash_runtime.cpp:786-787`) on `cs_`. Stream order is the whole mechanism, as `dflash_tap_collect.hpp:14-17` claims. Deferral does not weaken it (chunk N+1's writes are enqueued after chunk N's reads).
- **Pinned slots**: unchanged contracts — producer drains the slot's H2D before rewrite (`205`, event recorded at `347`); unconsumed STAGED slots are never evicted (`hpp:105-109`, `acquire` `112-117`); F2 adds the D2H event drains (change 12).
- **Request abort / reset racing in-flight fusion**: today `reset_staging()` at request start drains slot events and bumps `gen_`, waking waiters (`162-176`); the drafter pools are only written on `cs_`. Under deferral an aborted request's fusion may still be queued on `cs_` when the next request starts. All pool writes are on one stream in enqueue order, so the next request's appends land after the old ones; every read is host-synced. Host ring state is reset per request at `pos0 == 0` (`dflash_runtime.cpp:778`). No corruption expected; UNCONFIRMED for `--parallel > 1`, so the window runs `--parallel 1` (the bench drives one request at a time) and multi-session concurrency is a post-F1 test, not a gate.
- **Mid-prompt drafter-pool readers (map risk c) — checked, all clear**: checkpoints save the *target* session and stage sessions only (`generate.cpp:12751-12764`), not the drafter pools; drafter pool save exists only in the park path (`12544`), which the §2 change 7 barrier covers; conversation restore (`16782-16799`) runs at request start and already calls `dflash.idle()` (`16799`); `snapshot_meta()` (`12551`) and `context_retained()` (`16911`) read host counters only; `--dflash-remote-only` probes (`10740`, `16568-16585`) read host counters and never upload the local drafter (so `cs_` is null and deferral is inert; the remote lane's own plane read is already host-synced at `11313`).
- **SM/copy-engine contention** (map risk a): the deferred fusion competes with CUDA1's chunk compute on the same card, and the D2D/H2D copies ride the copy engines. Expected gain is partial; bitwise output is unaffected. Measured by F1's fresh-PP median vs the probe's fusion total (§4).

3. **(c) Prototype compile, inside the window, before any serve is up** — one binary, both flags. Rule: never compile during a serving/bench round (`RESULTS.md:37` — a parallel build starved a round and it was discarded).
4. **(d) Arm structure.** All arms = B's config plus flags, one arm at a time, ≥2 kept runs, medians.

## 5. Fallback tree (stated as decisions, not hedges)

- **F1 shows a small net gain** ⇒ the tail is SM/copy contention, not the drain. Next step is arm P (`cs_` priority, following `dflash2.cpp:213-224`) plus a chunk-size sweep; do not add streams (intervention 4 is limited by one PCIe link, `TAP_COLLECTION_MAP.md` §4).
- **F1 shows the copy barrier (`dflash_tap_collect.cpp:335` sync) is now the tail** ⇒ replace the host barrier with the same-device `cudaStreamWaitEvent` gate on `m.cs` before chunk N+1 (needs a small prefill↔collector plumbing hook, `prefill.hpp:226-261` callback family), same device, no new dependency.
- **F2's worker shows a loss** ⇒ keep the async enqueue (mutex released before the copy) with the producer draining its own event inside `stage()` after the copy, which recovers the mutex-serialization term without any new thread. If that also loses, drop F2 and keep F1; 120 MiB/chunk ≈ tens of ms cannot be worth a thread.
- **Any F arm trips a stale-read refusal** ⇒ the barrier placement is wrong (H1). Fix the barrier, do not loosen the guard: the guard is meant to be loud (`243-268`).

## 6. NOT-do list

- No removal of the `--pipeline-windows` + `--dflash` + split gate (`generate.cpp:5674-5676`; `dflash_tap_collect.hpp:62` serial-only).
- No arithmetic changes: no fusion of `hc_mean` into the HC read (`prefill.cpp:4112-4222`, `dflash_inco.cu:245-255`), no kernel rewrites, no reordering inside `fusion_rows` (`900-1010`).
- No default flips: `add_context` keeps `sync_context = true`; `add_context_f32` untouched; collector slot semantics untouched (invariant 2 preserved, §2 change 11).
- No new dependencies, no new streams in the prototype, no third slot (`hpp:88` `kSlots = 2` stays), no plane double-buffering.
- No pushes, no production disturbance (port 8009 live), no compile during a serving round.
- No STRATA_DF_DBG in any perf arm: it ADDS stream syncs (`dflash_runtime.cpp:790-793`, `805-814`).

## 7. Biggest risk

Correctness, not speed. The map's intervention-1 rationale ("plane reuse is protected by `cs_` stream order", `TAP_COLLECTION_MAP.md` §1) does not hold for the producer stage planes: the drafter-local D2D at `dflash_tap_collect.cpp:335` reads CUDA1's single-buffered stage plane from `cs_` while CUDA1's chunk N+1 writes it on `m.cs` (`prefill.cpp:4211`), and today the only ordering is the host sync being removed (`dflash_runtime.cpp:798`). Implemented as written, that is a silent nondeterminism bug that only the 80k sha gate catches — possibly not even there, on a 2-run sample. The gate's answer is §2 change 4 (same-device barrier over the 2×40 MiB D2D only) and the stale-read guard as the tripwire. Second risk, stated plainly: F1's gain may be partial-to-small if the 30k-launch fusion simply relocates its cost onto CUDA1's compute (`RESULTS.md:28-29` attributes the gap, not the recoverable share); step (a)'s probe is what prices it before the code.
